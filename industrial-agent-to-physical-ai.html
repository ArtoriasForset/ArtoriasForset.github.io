从工业 Agent 到 Physical AI：我对未来二十年的一些思考

控制并不是 Agent 最大的价值。比起让 AI 直接按下按钮，我更关心它能否理解现场正在发生什么、为什么发生，以及下一步应该做什么。

个人思考工业自动化Agent 与 Physical AI

很多人谈论工业 Agent 时，最先想到的是 AI 控制设备、AI 替代工程师、AI 自动生产。但随着不断思考，我越来越觉得：

控制并不是 Agent 最大的价值。真正的价值，来自于理解。

要理解这一点，首先要承认传统工业自动化已经取得的成就。工业 Agent 不是从零开始接管机器，而是建立在几十年来已经成熟的控制体系之上。

一、传统工业自动化已经解决了什么

PLC、运动控制、PID、EtherCAT、驱动器、传感器与执行器，共同构成了现代工业现场可靠而精密的基础设施。它们能够完成毫秒级控制、实时闭环与确定性执行。

在这些领域，人类工程师已经建立了成熟的理论、工程实践和安全规范。很多情况下，启动输送带、关闭气缸、控制伺服，根本不需要 AI。PLC 就能很好地完成这些任务。

这并不是说传统自动化不够先进。恰恰相反：确定性控制之所以重要，是因为它把一部分复杂性变成了可靠、可重复、可验证的执行过程。

二、工业现场真正缺的是什么

现场真正稀缺的，往往不是控制能力，而是跨设备、跨时间、跨业务关系的理解能力。

5,000 个 Tag不断变化的现场数据
300 个报警需要辨别轻重缓急
几十台设备存在复杂的上下游关系
持续积累的历史包含趋势、事件与生产背景

人类不可能同时关注全部信息。即便是经验丰富的工程师，也只能看到局部。设想现场发生了输送带停机、机器人等待、仓储积压、产量下降这一连串现象。

传统系统通常能够告诉我们发生了什么，但未必能直接解释为什么发生、哪个环节是根因、应该优先处理什么。报警列表可能越来越长，真正重要的因果关系却隐藏在不同设备的时间线里。

而这恰恰是 Agent 值得尝试的地方：把分散的数据与上下文组织起来，辅助人发现单看一个报警或一个 Tag 时很难看到的联系。

三、我理解的工业 Agent

工业 Agent 本质上不是一个新的控制器，而是一个能够持续观察现场、结合上下文进行推理并提出行动建议的智能体。

它可以读取实时与历史 Tag、实时与历史 Alarm、Event 历史、Command 历史，以及设备关系和工艺关系。只有把这些信息放在一起，数值才可能变成有意义的现场状态。

例如，系统观察到：

  • 10:21，光电传感器持续触发；
  • 10:22，电机电流持续增加；
  • 10:23，输送带停机。

单独看，每条记录只描述了一个事实。结合时间顺序、设备拓扑、工艺流程和历史案例后，Agent 可以提出一个假设：现场可能发生了物料堵塞。

进一步，它可以建议检查传感器区域，查询上游设备状态，比较电机历史电流曲线，并说明这一判断依据哪些证据、还有哪些不确定性。这比单纯提供一个控制按钮更有价值。

当然，时间上的先后不自动等于因果关系。好的工业 Agent 不应该把猜测伪装成事实，而应该给出证据、置信程度和待验证的问题。

四、为什么控制必须谨慎

从技术上讲，Agent 可以通过工具获得 Write Coil、Write Register，甚至伺服移动或机器人运动等执行接口。但“技术上能够执行”与“在真实现场中应该执行”是两回事。

现实世界不是实验室。不同模型的能力不同，同一个模型在不同上下文中也可能犯错。现场还涉及人员安全、设备损坏、工艺质量、生产损失以及操作责任。

认知权限，应当远大于控制权限。

在系统早期，我更愿意让 Agent 尽可能广泛地读取经过授权的数据、分析状态、提出建议，却只赋予它非常有限的执行权限。所谓“100% 的认知权限、10% 的控制权限”，是一种设计方向，而不是可以脱离具体风险照搬的数字。

控制权限应该按风险分级：只读分析可以更开放；低风险、可逆的操作可以设置约束后自动执行；涉及运动、安全、质量或重大生产影响的动作，则需要更严格的联锁、验证和人工审批。任何 AI 都不能绕过 PLC、安全回路和经过验证的保护机制。

五、Agent 真正应该掌握什么

与其一开始就让 Agent 直接控制驱动器，不如先让它掌握理解、预测、规划、建议与审批申请等能力。

当 Agent 发现输送带可能堵塞时，它可以先分析原因、评估风险、检查相关设备状态，再生成处理方案，例如建议暂停上料、排查传感器区域、检查输送带电机。系统同时展示判断依据、影响范围和可能的后果，交由有权限的人作出决定。

我认为一种值得优先实践的协作模式是：

观察→分析→提案→审批→执行

它既发挥了 AI 整理信息、发现联系和生成方案的能力，也保留了人的责任、经验与最终判断。执行之后，系统还应记录 Command、审批人、执行结果与后续状态，让结果重新进入历史数据，供之后分析和复盘。

六、从一个 Agent 到一套工业运行平台

如果要把上述想法落到软件工程上，核心就不只是接入一个大语言模型，而是建立一套可靠、可追踪的工业上下文。

设备、Tag、Alarm、Event 和 Command 可以成为统一的基础模型。边缘服务负责连接现场协议、采集数据和管理连接；平台服务负责设备与业务关系、历史记录、权限和工作流；Agent 在明确的工具边界内读取上下文并提出方案；HMI 则让工程师看见现场状态、证据和待审批动作。

在这样的架构里，Agent 不应该直接绕过业务服务随意写入设备。命令需要经过权限检查、参数校验、状态条件、审批策略和执行结果确认。涉及安全与实时性的逻辑，仍由 PLC、运动控制器及相应的安全系统负责。

这也是我对工业软件平台的一个理解：它不只是把设备连起来，更要把设备状态、生产语义、历史证据和可控行动连接起来。Agent 的能力取决于模型，也取决于它所处的系统是否可靠。

七、从工业 Agent 走向 Physical AI

我把 Physical AI 理解为：智能系统不再只处理屏幕中的文本与数据，而是通过感知、模型、规划和受约束的执行，持续参与真实物理环境中的任务。

工业是观察这条路径的一个重要起点。现场本来就有传感器、视觉系统、机器人、执行器和控制网络；现在需要进一步把这些设备产生的数据与任务目标、环境状态和业务约束联系起来。

视觉模型可以帮助识别物体与异常，传统控制器负责确定性动作，工业 Agent 理解更高层的任务与上下文，规划系统把目标拆成步骤，再由经过验证的接口执行。它们不是彼此替代，而是各自承担擅长的工作。

这意味着，Physical AI 并不等于“给机器人接一个 LLM”。一个能在现实世界中工作的系统，还需要可靠的传感、状态估计、运动规划、控制、故障处理、边界条件与安全机制。语言模型可以帮助理解目标和处理复杂上下文，但不能代替所有实时控制与安全验证。

八、我对未来二十年的一些思考

未来二十年会怎样，没有人能够准确预测。但我倾向于从系统能力的积累，而不是单一模型的进步来观察它。

第一阶段：从看见数据，到理解现场

更多工业系统会把分散的 Tag、报警、事件、设备关系与生产记录组织成可查询的上下文。Agent 首先成为工程师的分析助手：帮助定位问题、总结历史、解释异常、准备方案，而不是直接接管设备。

第二阶段：从生成建议，到受约束地完成任务

当工具接口、权限、仿真验证、审批和审计机制逐渐成熟，部分低风险、边界清晰、可回退的工作流可能实现更高程度的自动化。人类的角色会更多转向目标设定、异常处理、规则制定和结果负责。

第三阶段：从数字系统，到物理任务协作

随着感知、机器人、边缘计算和规划能力进步，AI 可能更深入地参与搬运、检查、装配、维护与复杂设备协作。但进展不会均匀发生：结构化环境通常更容易自动化，开放环境、长尾异常和高风险任务则需要更长时间的工程积累。

我不认为这条道路会简单地从“软件”走向“AI”，再由 AI 取代所有传统系统。更可能出现的是一个分层协作的世界：底层负责稳定与安全，中层负责设备和业务编排，上层负责理解目标、整合证据、规划任务，并在合适的边界内调用工具。

在这个过程中，真正稀缺的能力或许不是让模型拥有更多权限，而是设计一套系统，使智能可以被验证、被约束、被追踪，并且在犯错时能够安全地停止和恢复。

结语：先理解，再行动

从工业 Agent 到 Physical AI，我关注的核心始终不是让 AI 尽快接管某个按钮，而是让它逐渐理解设备、流程、环境与任务之间的关系。

先观察，再理解；先提出方案，再获得授权；先验证边界，再执行动作。

这不是对智能的限制，而是让智能真正进入现实世界所需要的工程基础。未来二十年值得期待的，也许不只是更强大的模型，而是我们能否构建出足够可靠的系统，让认知最终转化为有价值、可负责的行动。
